# OTIS 주석 규칙

작업 시작 전 매번 이 문서를 다시 읽는다. 대상: `westone-hq/OTIS` 전체 (Dart · Kotlin).

---

## 0. 파일 머리

**아무것도 두지 않는다.** 작성 이력은 각 선언 주석이 갖고, 변경 이력은 git 이 갖는다.

- Dart 파일 머리에 `///` 금지 — 바로 아래 첫 선언의 문서 주석으로 붙어버린다.
- 라이선스 · 자동생성 표시처럼 도구가 요구하는 줄만 예외로 남긴다.

---

## 1. 함수 · 클래스 · top-level 변수

라벨은 **항상 이 순서**로 쓴다. 해당 없는 줄은 생략한다.

```
작성 → 수정 → 함수/클래스/변수 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현
```

```dart
/// 작성: 2026-08-15 14:32:07 · 홍길동
/// 수정: 2026-08-20 09:11:45 · 김영희
/// 함수: onEvent
/// 목적: 네이티브 원본 이벤트 1건을 종류별로 누적한다.
///       가공은 하지 않고, 환산에 쓸 수 없는 것만 걸러 집계한다.
/// 인자: event — 네이티브에서 도착한 원본 이벤트
/// 반환: 없음. 폐기 시 해당 집계값만 증가한다
/// 식:   수식에서 옮긴 함수만. 원본 기호 그대로 쓰고 코드 변수와 대응 표시
/// 근거: 판단이 들어간 곳만. 표준/인용/측정/미정 + 찾아갈 수 있을 만큼
void onEvent(NativeEvent event) {
```

Kotlin 은 `/** ... */`, 라벨은 동일.

### 1-1. 작성 · 수정

| 항목 | 형식 | 규칙 |
|---|---|---|
| 작성 | `작성: YYYY-MM-DD HH:MM:SS · 이름` | 날짜와 이름을 가운뎃점으로 한 줄에 붙인다. 초 단위까지 |
| 수정 | `수정: YYYY-MM-DD HH:MM:SS · 이름` | **그 선언의 내용이나 주석이 실제로 바뀐 경우에만** 추가 |

- 최신 것만 남기고 **`수정`은 최대 1줄**. 그 이전 이력은 git 이 갖는다.
- 작성자와 수정자가 같으면 `수정` 줄을 쓰지 않는다.
- **값을 모르면 줄을 통째로 생략한다.** `미상`, `unknown` 같은 채움값을 쓰지 않는다.
- 파일 전체를 한 사람이 고쳤어도, 그 파일 안 선언마다 각자 `수정` 줄을 갖는다.

### 1-2. 첫 라벨

| 대상 | 라벨 |
|---|---|
| 함수 · 메서드 · 게터 · 생성자 | `함수: 이름` |
| 클래스 · enum · mixin | `클래스: 이름` |
| 여러 줄 설명이 필요한 top-level 변수 · 상수 | `변수: 이름` |
| 요청 하나 받아 응답 하나 돌려주는 분기 (Kotlin `when (call.method)` 의 각 case 등) | `함수: 그 요청 이름` — 진짜 함수는 아니지만 동작이 함수와 같아서 예외로 허용 |

**`목적:` 만 있고 첫 라벨이 없는 주석 블록은 금지한다.** 라벨이 없으면 그 블록이 무엇을 설명하는지 기계가 찾지 못하고, 링크 범위도 잡히지 않는다.

### 1-3. 필수 여부

| 항목 | 필수 | 기준 |
|---|---|---|
| 작성 | ✅ | 아는 경우. 모르면 생략 |
| 수정 | 바뀐 경우만 | |
| 함수/클래스/변수 | ✅ | 이름 그대로 |
| 목적 | ✅ | 무엇을 · 왜. 실행 줄이 여럿이면 줄/의미 단위로 항목화 |
| 인자 | 있으면 | `이름 — 설명(단위·범위·null 의미)` |
| 반환 | 있으면 | 의미(단위) + 실패/부작용 |
| 식 | 있으면 | 원본 기호 그대로 + 코드 변수 대응 |
| 근거 | 판단이 들어간 곳만 | 5장 참고 |
| 미구현 | 미구현이면 | 6장 참고 |

- 적용 범위: public · private 함수, override, 클래스, 여러 줄 설명이 필요한 top-level 변수 전부.
- 예외: 한 줄 게터 · 인자 없는 생성자는 `작성` + `함수` + `목적` 세 줄만.
- 위젯 트리처럼 중첩된 코드는 각 위젯 뒤에 `// 역할` 한 줄. 라벨 텍스트로 이미 아는 건 안 단다.

## 2. 변수

```dart
/// 마지막 수신 시각 (ns, 단조시계). null 이면 아직 수신 전
int? lastEventNs;

var dropped = 0; // 폐기한 샘플 수
```

- 필드 · 상수 · 프로퍼티: 위에 `///` 한 줄. 지역변수: 뒤에 `//`, 예외 없이 전부.
- 한 줄짜리 필드 주석에는 `작성` 을 붙이지 않는다. 1장은 여러 줄 설명이 붙는 선언만 대상이다.
- 단위 · 범위 · 특수값 의미 · 기준을 반드시 적는다 (`mg`, `0~1`, `null 이면 미측정`, `단조시계 기준`).
- 이름이 실제 역할과 안 맞거나 같은 개념인데 표기가 다르면(`Str`/없음, `Error`/`Err`) 이름도 통일한다. 쓰는 곳 전부 같이 고친다.

## 3. 로직 이동 표시

흐름이 다른 화면 · 함수로 넘어가는 지점에 단다. **이 표시가 UML 액티비티 · 시퀀스 다이어그램의 근거다.**

```dart
// → 로직 이동: GridResampler.resample()
final result = _resampler.resample();
```

- 대상 이름만 짧게. 설명 문장 금지.
- **호출부마다 하나씩 단다.** 같은 대상을 세 곳에서 부르면 표시도 세 개다. 한 곳만 달면 다이어그램에서 갈래가 사라진다.
- 표시한 대상은 **실제로 실행될 수 있어야 한다.** 부르는 곳이 없거나 조건상 절대 도달하지 못하는 경로에는 달지 않는다. 그런 코드는 7장에 따라 삭제한다.
- 대상 이름은 코드의 실제 식별자 그대로 쓴다. 한국어 별칭은 명칭 통일표에서 따로 관리한다.

## 4. 말투

- 본문 주석은 **"왜"만**. "무엇"은 코드가 말한다. 코드 반복 금지.
- 한국어 평서형(`~한다`). 영어는 식별자 · 단위 · 고유명사만.
- 정보만 정확히 적는다. `~일 뿐이다`, `~할 뿐` 같은 완화 · 강조 표현 금지 — `표시일 뿐이다` 대신 `표시이다`.
- **먼저 쉬운 말로 풀어써 본다.** `위젯 트리 상 빌드 위치 정보` 대신 `이 화면이 어디에 놓이는지 알려주는 값`처럼, 프레임워크 용어 자체를 안 써도 되면 안 쓴다. `async` → `비동기`처럼, 코드에 나오는 영어 키워드도 그대로 인용하지 말고 우리말로 바꿔 쓴다.
- 용어를 꼭 써야 하면(그 용어 자체가 코드에 나오는 식별자라서 피할 수 없을 때) 그 파일에서 처음 나올 때만 괄호로 풀어 쓴다 — 예: `오버라이드(override, 상위 클래스가 정해둔 메서드를 하위 클래스가 다시 정의하는 것)`. **길어져도 된다.** 같은 파일 두 번째부터는 이름만. 파일이 바뀌면 다시 푼다.
- 줄 80자, 넘으면 줄바꿔 라벨 다음 칸에 맞춰 들여쓰기.

---

## 5. 근거 인용

- 종류: 표준 / 인용 / 측정 / 미정. 찾아갈 수 있을 만큼 구체적으로 적는다.
- **결정 코드만 던지지 않는다** (`(RD-6)` 등). 코드는 우리만 안다 — 그 결정이 실제로 뭘 정했는지 내용을 풀어 쓰고, 코드는 있어도 그만인 부가 정보로만 둔다.
- 원본 문서가 저장소에 없으면(삭제됨 등) 코드 인용 자체를 하지 않는다. 확인 못 한 내용은 추측하지 말고 `미확인:` 으로 명시한다.
- 옛 코드/문서 체계 표기(`S1`, `A-01` 등)는 새 주석에 끌어오지 않는다.

---

## 6. 미구현 표기

예외를 던지거나, 값을 흉내만 내거나, 빈 본문인 선언에는 `미구현:` 줄을 붙인다.

```dart
/// 작성: 2026-08-18 23:29:46 · 박건준
/// 함수: save
/// 목적: 측정 한 건을 기기에 저장한다.
/// 인자: result — 저장할 측정 결과
/// 반환: 저장된 항목의 식별자
/// 미구현: 저장 계층이 없어 UnimplementedError 를 던진다.
///         부르는 쪽에서 잡아 "저장 기능은 아직 구현되지 않았습니다"를 띄운다.
Future<String> save(MeasurementResult result) => throw UnimplementedError();
```

- **무엇이 없는지 + 대신 무슨 일이 일어나는지** 둘 다 적는다. "아직 구현 안 됨" 한 줄로 끝내지 않는다.
- 조용히 성공한 척하는 경우(항상 `true` 반환, 빈 Map 반환, 빈 본문)가 가장 위험하다. 반드시 적는다.
- 부르는 곳이 하나도 없는 미구현 선언은 표기 대상이 아니라 **삭제 대상**이다.

## 7. 금지

| 금지 | 이유 |
|---|---|
| 코드를 그대로 옮긴 주석 | 정보량 0, 코드 바뀌면 거짓이 된다 |
| 주석 처리한 죽은 코드 | 발견 즉시 삭제. 이력은 git 이 갖는다 |
| 부르는 곳이 없는 선언 | 삭제한다. 주석으로 설명해 남기지 않는다 |
| 날짜 · 담당 없는 TODO | `// TODO(홍길동, 2026-09-01):` 형식만 허용 |
| 추측 서술 (`아마도`, `~인 듯`) | 5장 참고 |
| 비유 · 관용 표현 (`들쭉날쭉하다` 등) | 정확한 말로 쓴다 — `들쭉날쭉한 간격` 대신 `일정하지 않은 간격` |
| 영어 서술문 | 읽는 사람이 한국어 리뷰어다 |
| 함수 아래 주석 | 설명은 항상 선언 위에 |
| 파일 머리 작성 이력 | 0장 참고. 선언마다 갖는다 |
| `목적:` 만 있고 첫 라벨이 없는 블록 | 1-2 참고 |
| 테스트 · 디버그 전용 우회로 | 제품 흐름에 섞지 않는다. 주입이 필요하면 생성자 인자로만 |

## 8. 링크

- 시작 줄 = **주석 첫 줄**(= `작성:` 줄), 끝 줄 = 선언 닫는 괄호
  `.../blob/<커밋>/<경로>#L<주석시작>-L<선언끝>`
- 호출 지점을 가리키는 화살표 링크는 예외 — 호출한 줄 그대로 (`#L124`, `#L282-L291`).
- 주석 작업 완료 후 전면 재링크, 커밋 해시 최신화.
- 줄번호는 자주 밀린다. 인용한 줄번호는 **전부 실제 코드와 대조한 뒤** 결과를 보고한다.

---

## 9. 점검표

1. 파일 머리에 작성 이력이 남아 있지 않은가
2. 모든 선언 주석이 `작성 → 수정 → 라벨 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현` 순서인가
3. `목적:` 만 있고 첫 라벨이 없는 블록은 없는가
4. 수식 있는 함수에 `식:` 이 있는가
5. 모든 필드 · 지역변수에 단위 · 범위 · 설명이 있는가
6. 미구현 선언에 `미구현:` 이 있고, 대신 무슨 일이 일어나는지 적혀 있는가
7. 부르는 곳이 없는 선언 · 주석 처리된 죽은 코드가 없는가
8. 본문 주석이 "왜"만 말하는가, 코드 반복이 없는가
9. 80자 넘는 줄이 없는가
10. 프레임워크 용어를 쉬운 말로 풀 수 있는데 그냥 쓰진 않았는가
11. 결정 코드만 던지고 내용을 안 풀어 쓴 곳은 없는가
12. `로직 이동` 이 대상만 짧게, 호출부마다 하나씩 달려 있는가
13. `로직 이동` 대상이 실제로 도달 가능한가
14. 링크 시작 줄이 주석 첫 줄인가
