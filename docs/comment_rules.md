# OTIS 주석 규칙

작업 시작 전 매번 이 문서를 다시 읽는다. 대상: `westone-hq/OTIS` 전체 (Dart · Kotlin).

---

## 1. 파일 머리

```dart
// 작성: 2026-08-15 14:32:07
// 작성자: 홍길동
// 수정: 2026-08-20 09:11:45
// 수정자: 홍길동

import 'dart:math' as math;
```

- 날짜는 `YYYY-MM-DD HH:MM:SS`(분·초까지). 날짜와 이름은 항상 별도 줄.
- 수정 세트는 바뀔 때만 추가, 최신 것만 남기고 최대 2세트.
- Dart는 `import` 위, Kotlin은 `package` 위. Dart 파일 머리에 `///` 금지(첫 선언 문서 주석으로 붙어버림).

## 2. 함수 · 클래스 · top-level 변수

첫 줄 라벨만 대상에 맞게 쓰고, 나머지(목적/인자/반환/식/근거)는 형식이 같다.

| 대상 | 첫 줄 라벨 |
|---|---|
| 함수 · 메서드 · 게터 | `함수: 이름` |
| 클래스 | `클래스: 이름` |
| 여러 줄 설명이 필요한 top-level 변수 · 상수 | `변수: 이름` |
| 요청 하나 받아 응답 하나 돌려주는 분기(Kotlin `when(call.method)`의 case 등) | `함수: 그 요청 이름` — 진짜 함수는 아니지만 동작이 함수와 같아서 예외로 허용 |

```dart
/// 함수: onEvent
/// 목적: 네이티브 원본 이벤트 1건을 종류별로 누적한다.
///       가공은 하지 않고, 환산에 쓸 수 없는 것만 걸러 집계한다.
/// 인자: event — 네이티브에서 도착한 원본 이벤트
/// 반환: 없음. 폐기 시 해당 집계값만 증가한다
/// 식:   수식에서 옮긴 함수만. 원본 기호 그대로 쓰고 코드 변수와 대응 표시
/// 근거: 판단이 들어간 곳만. 표준/인용/측정/미정 + 찾아갈 수 있을 만큼
void onEvent(NativeEvent event) {
```

Kotlin은 `/** ... */`, 라벨(함수/클래스/변수/목적/인자/반환/식/근거)은 동일.

| 항목 | 필수 | 기준 |
|---|---|---|
| 함수/클래스/변수 | ✅ | 이름 그대로 |
| 목적 | ✅ | 무엇을 · 왜. 실행 줄이 여럿이면 줄/의미 단위로 항목화 |
| 인자 | 있으면 | `이름 — 설명(단위·범위·null 의미)`. 없으면 줄 생략 |
| 반환 | 있으면 | 의미(단위) + 실패/부작용. 없으면 줄 생략 |
| 식 | 있으면 | 원본 기호 그대로 + 코드 변수 대응 |
| 근거 | 판단이 들어간 곳만 | 아래 5장 참고 |

- 적용 범위: public · private 함수, override, 클래스, 여러 줄 설명이 필요한 top-level 변수 전부. 예외: 한 줄 게터 · 인자 없는 생성자는 목적 한 줄만.
- 위젯 트리처럼 중첩된 코드는 각 위젯 뒤에 `// 역할` 한 줄. 라벨 텍스트로 이미 아는 건 안 단다.
- 화면 · 함수로 흐름이 넘어가는 지점엔 `// → 로직 이동: 대상` — 대상 이름만 짧게. 설명 문장 금지.

## 3. 변수

```dart
/// 마지막 수신 시각 (ns, 단조시계). null 이면 아직 수신 전
int? lastEventNs;

var dropped = 0; // 폐기한 샘플 수
```

- 필드 · 상수 · 프로퍼티: 위에 `///` 한 줄. 지역변수: 뒤에 `//`, 예외 없이 전부.
- 단위 · 범위 · 특수값 의미 · 기준을 반드시 적는다 (`mg`, `0~1`, `null 이면 미측정`, `단조시계 기준`).
- 이름이 실제 역할과 안 맞거나 같은 개념인데 표기가 다르면(`Str`/없음, `Error`/`Err`) 이름도 통일한다. 쓰는 곳 전부 같이 고친다.

---

## 4. 말투

- 본문 주석은 **"왜"만**. "무엇"은 코드가 말한다. 코드 반복 금지.
- 한국어 평서형(`~한다`). 영어는 식별자 · 단위 · 고유명사만.
- **먼저 쉬운 말로 풀어써 본다.** `위젯 트리 상 빌드 위치 정보` 대신 `이 화면이 어디에 놓이는지 알려주는 값`처럼, 프레임워크 용어 자체를 안 써도 되면 안 쓴다.
- 용어를 꼭 써야 하면(그 용어 자체가 코드에 나오는 식별자라서 피할 수 없을 때) 그 파일에서 처음 나올 때만 괄호로 풀어 쓴다 — 예: `오버라이드(override, 상위 클래스가 정해둔 메서드를 하위 클래스가 다시 정의하는 것)`. **길어져도 된다.** 같은 파일 두 번째부터는 이름만. 파일이 바뀌면 다시 푼다.
- 줄 80자, 넘으면 줄바꿔 라벨 다음 칸에 맞춰 들여쓰기.

---

## 5. 근거 인용

- 종류: 표준 / 인용 / 측정 / 미정. 찾아갈 수 있을 만큼 구체적으로 적는다.
- **결정 코드만 던지지 않는다** (`(RD-6)` 등). 코드는 우리만 안다 — 그 결정이 실제로 뭘 정했는지 내용을 풀어 쓰고, 코드는 있어도 그만인 부가 정보로만 둔다.
- 원본 문서가 저장소에 없으면(삭제됨 등) 코드 인용 자체를 하지 않는다. 확인 못 한 내용은 추측하지 말고 `미확인:`으로 명시한다.
- 옛 코드/문서 체계 표기(`S1`, `A-01` 등)는 새 주석에 끌어오지 않는다.

---

## 6. 금지

| 금지 | 이유 |
|---|---|
| 코드를 그대로 옮긴 주석 | 정보량 0, 코드 바뀌면 거짓이 된다 |
| 주석 처리한 죽은 코드 | 발견 즉시 삭제. 이력은 git 이 갖는다 |
| 날짜 · 담당 없는 TODO | `// TODO(홍길동, 2026-09-01):` 형식만 허용 |
| 추측 서술 (`아마도`, `~인 듯`) | 5장 참고 |
| 영어 서술문 | 읽는 사람이 한국어 리뷰어다 |
| 함수 아래 주석 | 설명은 항상 선언 위에 |

## 7. 플로우차트 링크

- 시작 줄 = 주석 첫 줄, 끝 줄 = 함수 닫는 괄호: `.../blob/<커밋>/<경로>#L<주석시작>-L<함수끝>`
- 호출 지점을 가리키는 화살표 링크는 예외 — 호출한 줄 그대로 (`#L124`, `#L282-L291`).
- 주석 작업 완료 후 전면 재링크, 커밋 해시 최신화.

---

## 8. 점검표

1. 파일 머리(초 단위 시각 · 작성자) 있는가
2. 모든 함수에 함수/목적/인자/반환이 순서대로 있는가 (없으면 생략됐는가)
3. 수식 있는 함수엔 식: 이 있는가
4. 모든 필드 · 지역변수에 단위 · 범위 · 설명이 있는가
5. 본문 주석이 "왜"만 말하는가, 코드 반복이 없는가
6. 주석 처리된 죽은 코드가 없는가
7. 80자 넘는 줄이 없는가
8. 프레임워크 용어를 쉬운 말로 풀 수 있는데 그냥 쓰진 않았는가
9. 결정 코드만 던지고 내용을 안 풀어 쓴 곳은 없는가
10. 로직 이동 표시가 대상만 짧게 되어 있는가
11. 링크 시작 줄이 주석 첫 줄인가
