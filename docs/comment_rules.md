# OTIS 주석 규칙 (v4)

작업 시작 전 매번 이 문서를 다시 읽는다. 대상: `westone-hq/OTIS` 전체 (Dart · Kotlin).

2026-09-15 코드 전수 확인 후 갱신. 확인 범위는 `lib/` · `android/app/src/` 소스 26개,
주석 줄 약 2,000줄이다. 아래 규칙은 그 코드에 실제로 자리 잡은 표기를 옮긴 것이다.

---

## 0. 파일 머리

**아무것도 두지 않는다.** 작성 이력은 각 선언 주석이 갖고, 변경 이력은 git 이 갖는다.

- Dart 파일 머리에 `///` 금지 — 바로 아래 첫 선언의 문서 주석으로 붙어버린다.
- 다만 `import` 가 하나도 없어 **첫 선언이 1행부터 시작하는 파일**은, 1행의 `///`
  가 곧 그 선언의 문서 주석이므로 위반이 아니다 (`auth_repository.dart`,
  `capture_config.dart`, `native_event.dart`, `sensor_sample.dart`).
- 라이선스 · 자동생성 표시처럼 도구가 요구하는 줄만 예외로 남긴다.

## 1. 함수 · 클래스 · 상수 선언 주석

라벨은 **항상 이 순서**로 쓴다. 해당 없는 줄은 생략한다.

```
작성 → 수정 → 함수/클래스/변수 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현
```

```dart
/// 작성: 2026-08-19 08:04:05 · 박건준
/// 수정: 2026-08-19 13:25:00 · 박희정
/// 함수: onEvent
/// 목적: 네이티브 원본 이벤트 1건을 종류별로 누적한다.
///       가공은 하지 않고, 환산에 쓸 수 없는 것만 걸러 집계한다.
/// 인자: event — 네이티브에서 도착한 원본 이벤트
/// 반환: 없음. 폐기 시 해당 집계값만 증가한다
/// 식:   수식에서 옮긴 함수만. 원본 기호 그대로 쓰고 코드 변수와 대응 표시
/// 근거: 판단이 들어간 곳만. 표준/인용/측정/미정/미확인 + 찾아갈 수 있을 만큼
void onEvent(NativeEvent event) {
```

Kotlin 은 `/** ... */`, 라벨은 동일.

### 1-1. 작성 · 수정

| 항목 | 형식 | 규칙 |
|---|---|---|
| 작성 | `작성: YYYY-MM-DD HH:MM:SS · 이름` | 날짜와 이름을 가운뎃점으로 한 줄에 붙인다. 초 단위까지 |
| 수정 | `수정: YYYY-MM-DD HH:MM:SS · 이름` | **그 선언의 내용이나 주석이 실제로 바뀐 경우에만** 추가 |

- 최신 것만 남기고 **`수정`은 최대 1줄**. 그 이전 이력은 git 이 갖는다.
- 작성자와 수정자가 같으면 `수정` 줄을 쓰지 않는다.
- **값을 모르면 줄을 통째로 생략한다.** `미상`, `unknown` 같은 채움값을 쓰지 않는다.
- 파일 전체를 한 사람이 고쳤어도, 그 파일 안 선언마다 각자 `수정` 줄을 갖는다.

### 1-2. 첫 라벨

| 대상 | 라벨 |
|---|---|
| 함수 · 메서드 · 게터 · 생성자 · 팩토리 | `함수: 이름` |
| 클래스 · enum · mixin | `클래스: 이름` |
| 클래스 상수(`static const`) · 싱글턴 `instance` · 설정 상수 | `변수: 이름` |
| 요청 하나 받아 응답 하나 돌려주는 분기 (Kotlin `when (call.method)` 의 각 case 등) | `함수: 그 요청 이름` — 진짜 함수는 아니지만 동작이 함수와 같아서 예외로 허용 |

- 생성자 · 팩토리도 라벨을 갖는다. 이름은 `GridResampleResult`,
  `GridResampleResult.failure` 처럼 호출할 때 쓰는 이름 그대로 적는다.
- 인스턴스 필드는 `변수:` 를 쓰지 않는다 — 2장에서 따로 다룬다.

**`목적:` 만 있고 첫 라벨이 없는 주석 블록은 금지한다.** 라벨이 없으면 그 블록이 무엇을 설명하는지 기계가 찾지 못하고, 링크 범위도 잡히지 않는다.
라벨을 하나도 쓰지 않는 산문형 필드 주석(2-2)은 이와 다르며 허용한다. **라벨을 쓰기 시작했으면 첫 라벨이 반드시 있어야 한다**는 뜻이다.

### 1-3. 필수 여부

| 항목 | 필수 | 기준 |
|---|---|---|
| 작성 | ✅ | 아는 경우. 모르면 생략 |
| 수정 | 바뀐 경우만 | |
| 함수/클래스/변수 | ✅ | 이름 그대로 |
| 목적 | ✅ | 무엇을 · 왜. 실행 줄이 여럿이면 줄/의미 단위로 항목화 |
| 인자 | 있으면 | `이름 — 설명(단위·범위·null 의미)` |
| 반환 | 있으면 | 의미(단위) + 실패/부작용 |
| 식 | 있으면 | 원본 기호 그대로 + 코드 변수 대응 |
| 근거 | 판단이 들어간 곳만 | 5장 참고 |
| 미구현 | 미구현이면 | 6장 참고 |

- 적용 범위: public · private 함수, override, 클래스, 생성자, 클래스 상수 전부.
- 예외: 한 줄 게터 · 인자 없는 생성자는 `작성` + `함수` + `목적` 세 줄만.
- 위젯 트리처럼 중첩된 코드는 2-4 를 따른다.

### 1-4. 줄바꿈과 들여쓰기

줄 80자. 넘으면 줄을 바꾸고 **다음 줄은 라벨 자리만큼 띄운다.** 실제 코드가 쓰는 폭은 아래로 고정되어 있다.

| 라벨 | 이어지는 줄 들여쓰기 |
|---|---|
| `작성` `수정` `함수` `클래스` `변수` `목적` `인자` `반환` `근거` `미구현` `미확인` | `///` 뒤 **7칸** |
| `식` | `///` 뒤 **5칸** |
| `목적` 안의 불릿 | 불릿 기호 `- ` 를 **7칸** 자리에서 시작, 그 불릿이 넘치면 **9칸** |
| `목적` 안의 번호 목록 | 번호 `1. ` 를 **7칸** 자리에서 시작, 그 항목이 넘치면 **10칸** |

```dart
/// 목적: 홈 화면(현장 정보 입력) 레이아웃을 구성한다.
///       - `appBar` — 화면 제목과, 설정·저장 결과 화면으로 이동하는
///         버튼 2개
///       - `body` — 스크롤 가능한 입력 폼
/// 인자: xMg — X축 진동값 (mg)
///       yMg — Y축 진동값 (mg)
/// 식: alpha = (t - t_앞) / (t_뒤 - t_앞)
///     값 = 값_앞 + alpha x (값_뒤 - 값_앞)
```

- 인자가 여럿인데 설명이 같으면 `xMg, yMg, zMg — 세 축 가속도 값 (mg)` 처럼 한 줄에 묶는다.

### 1-5. `목적:` 쓰는 법

- 첫 줄은 **한 문장 요약**. 이어서 필요하면 근거·제약을 문장으로 붙인다.
- 하는 일이 여럿이면 불릿으로 나눈다. 형식은 `` - `식별자` — 설명 `` 또는 `- 설명`.
- 순서가 있는 절차는 불릿 대신 번호 목록(`1.` `2.` …)을 쓴다. 이어지는 줄은 번호 너비만큼 한 칸 더 들여 **10칸**에 맞춘다 (`_finishMeasurement`).

```dart
/// 목적: "테스트 완료" 버튼을 눌렀을 때 측정을 마무리한다. 순서대로
///       진행한다.
///       1. 이미 마무리 중이거나 끝났으면 다시 실행하지 않는다
///          (중복 탭 방지)
///       2. 결과 파일을 저장하고 완료 요약 대화상자를 띄운다
```

- 설명이 길어져 갈래가 여럿이 되면, 불릿 위에 제목 줄을 두고 그 아래로 불릿을 한 단 더 들여쓴다 (`SensorStreamHandler` 의 "안드로이드 센서 검출 방식", "중력 채널(TYPE_GRAVITY) 의 성질").

## 2. 변수 주석

변수는 어디에 있느냐에 따라 세 갈래로 쓴다.

### 2-1. 클래스 상수 · 싱글턴 — 라벨 블록

```dart
/// 작성: 2026-08-19 08:04:05 · 박건준
/// 변수: normalIntervalMinUs
/// 목적: 정상 수신 간격의 하한이다. 이보다 짧은 간격은 지연 폭주로 보고 집계한다.
/// 근거: 인용 — 도입 시 목표 주기 간격의 절반과 두 배 수준으로 임시 설정했다.
static const int normalIntervalMinUs = 1953;
```

- `static const`, 싱글턴 `instance`, 파일 규격 상수(`formatId`, `columnCount` 등)가 대상.
- 값이 왜 그 값인지 설명이 필요하므로 `근거:` 를 거의 항상 같이 쓴다.

**예외 — 같은 성격의 상수가 무리로 있을 때.** 좌표표처럼 성격이 같은 상수가 수십 개 모여 있으면, 항목마다 라벨 블록을 다는 것이 4장의 코드 반복 금지와 부딪친다. `목적: X 좌표다`를 마흔 번 적으면 정보량이 0 이다. 이럴 때는 이렇게 쓴다.

- **묶음 앞에 라벨 블록을 한 번 둔다.** 거기에 단위 · 좌표계 · 출처처럼 묶음 전체에 걸리는 공통 정보를 적는다. 묶음이 클래스 하나면 그 클래스 주석이 묶음 블록이 된다
- **항목은 한 줄 주석으로 적는다.** 그 항목만의 뜻과, 공통 정보로 덮이지 않는 부분만 쓴다
- **항목에 따로 근거가 있으면 그 항목에만 라벨 블록을 둔다.** 나머지는 한 줄로 남긴다

```dart
/// 작성: 2026-09-15 19:43:50 · nada
/// 클래스: ReportPage1
/// 목적: 리포트 1쪽의 자리들을 담는다. 좌표는 모두 서식 이미지 픽셀이고
///       원점은 좌상단이다.
class ReportPage1 {
  /// 신호등 원의 중심 가로 좌표 (픽셀)
  static const int dotCenterX = 243;

  /// 구분 이름이 시작하는 가로 좌표 (픽셀)
  static const int colCategoryX = 313;

  /// 작성: 2026-09-15 19:43:50 · nada
  /// 변수: travelDistanceY
  /// 목적: 운행 거리 행의 세로 좌표 (픽셀).
  /// 근거: 인용 — 원본 리포트에서 잰 값이다. 앞 행과의 간격이 표에서 가장
  ///       좁아 계산으로 구하면 어긋난다
  static const int travelDistanceY = 1743;
}
```

### 2-2. 인스턴스 필드 — 라벨 없는 산문

```dart
/// 마지막 수신 시각 (나노초, 단조시계). null 이면 아직 수신 전
int? lastEventNs;

/// 경과 시간(`_elapsedSeconds`)을 1초마다 하나씩 올리는 타이머.
/// `_initCaptureAndTimers()`가 만들고, `_cleanup()`이 멈춘 뒤 비운다.
/// 아직 시작 전이거나 이미 정리됐으면 null
Timer? _timeTimer;
```

- 한 줄이든 여러 줄이든 **라벨도 `작성`도 붙이지 않는다.** 산문으로 쓴다.
- 여러 줄일 때는 누가 채우고 누가 비우는지, null 일 때 무슨 뜻인지까지 적는다.
- Kotlin 은 `/** ... */` 한 줄 형태를 쓴다 — `/** 가속도 센서. start() 가 채운다. 이 기기에 없으면 null */`

### 2-3. 지역변수 — 후행 `//`

```dart
final sensorSub = _sensorSub; // 끊기 전에 잠시 옮겨두는 구독, 없으면 null
```

- 예외 없이 전부 단다.
- 코드와 주석을 합쳐 80자를 넘기면 **Kotlin 은 `=` 뒤에서 줄을 바꾼다.** 주석은 `=` 옆에 남기고 값을 다음 줄로 내린다.

```kotlin
val sensorManager = // 센서 목록 조회·구독 담당 시스템 서비스. 못 가져오면 null
    getSystemService(Context.SENSOR_SERVICE) as SensorManager?
```


### 2-5. 공통

- 단위 · 범위 · 특수값 의미 · 기준을 반드시 적는다 (`mg`, `0~1`, `null 이면 미측정`, `단조시계 기준`).
- 단위 표기는 코드가 쓰는 대로 맞춘다 — 물리량은 기호(`mg`, `Hz`), 시간은 우리말(`나노초`, `마이크로초`, `초`). 변수 이름이 `Ns`·`Us` 로 끝나도 설명에는 `(나노초)`·`(마이크로초)` 라고 쓴다.
- 이름이 실제 역할과 안 맞거나 같은 개념인데 표기가 다르면(`Str`/없음, `Error`/`Err`) 이름도 통일한다. 쓰는 곳 전부 같이 고친다.

## 3. 로직 이동 표시

흐름이 다른 화면 · 함수로 넘어가는 지점에 단다. **이 표시가 UML 액티비티 · 시퀀스 다이어그램의 근거다.**

자리는 두 가지다.

```dart
// 호출문이 그 줄을 혼자 쓰거나 인자 여러 줄에 걸칠 때 — 위 줄에
// → 로직 이동: GridResampler.resample()
final result = _resampler.resample();

// 호출문이 짧아 한 줄에 들어갈 때 — 코드 뒤에
unawaited(_cleanup()); // → 로직 이동: _cleanup()
routerConfig: appRouter, // → 로직 이동: appRouter
```

- 대상 이름만 짧게. 설명 문장 금지.
- **함수 · 메서드는 `()` 를 붙인다** (`_startMeasure()`, `SensorChannelManager.stopCapture()`, `HomeScreen.build()`). 함수가 아닌 대상 — 객체, 프로퍼티, Kotlin `when` case — 은 괄호 없이 이름만 (`appRouter`, `MeasurementSession.instance.currentSite`, `MainActivity.checkAvailable`).
- **호출부마다 하나씩 단다.** 같은 대상을 세 곳에서 부르면 표시도 세 개다. 한 곳만 달면 다이어그램에서 갈래가 사라진다.
- 표시한 대상은 **실제로 실행될 수 있어야 한다.** 부르는 곳이 없거나 조건상 절대 도달하지 못하는 경로에는 달지 않는다. 그런 코드는 7장에 따라 삭제한다.
- 대상 이름은 코드의 실제 식별자 그대로 쓴다. 한국어 별칭은 명칭 통일표에서 따로 관리한다.

## 4. 말투

- 본문 주석은 **"왜"만**. "무엇"은 코드가 말한다. 코드 반복 금지.
- 한국어 평서형(`~한다`). 영어는 식별자 · 단위 · 고유명사만.
- 정보만 정확히 적는다. `~일 뿐이다`, `~할 뿐` 같은 완화 · 강조 표현 금지 — `표시일 뿐이다` 대신 `표시이다`.
- **코드에 있는 이름을 주석에서 부를 때는 백틱으로 감싼다** — `` `_cleanup()` ``, `` `AppColors.bg` ``. 파일을 가리킬 때도 `라우터(router.dart)` 처럼 실제 파일명을 적는다.
- **먼저 쉬운 말로 풀어써 본다.** `위젯 트리 상 빌드 위치 정보` 대신 `이 화면이 어디에 놓이는지 알려주는 값`처럼, 프레임워크 용어 자체를 안 써도 되면 안 쓴다. `async` → `비동기`처럼, 코드에 나오는 영어 키워드도 그대로 인용하지 말고 우리말로 바꿔 쓴다.

### 4-1. 용어 풀이

용어를 꼭 써야 하면(그 용어 자체가 코드에 나오는 식별자라서 피할 수 없을 때) **그 파일에서 처음 나올 때만** 괄호로 풀어 쓴다. 쓰는 형태는 셋이다.

| 형태 | 예 | 언제 |
|---|---|---|
| `우리말(영어, 풀이)` | `배치(batch, 여러 개를 묶은 덩어리)` | 영어 원어도 같이 알아둬야 할 때 |
| `우리말(풀이)` | `격자(일정한 시간 간격으로 줄 세운 표의 각 행)`<br>`보간(양옆 실측값 사이를 비례로 채워 넣는 계산)` | 우리말만으로 충분할 때 — 기본형 |
| `` `식별자`(풀이) `` | `` `EventChannel`(네이티브가 데이터를 계속 흘려보내는 통로) `` | 코드 이름을 그대로 불러야 할 때 |

**길어져도 된다.** 같은 파일 두 번째부터는 이름만. 파일이 바뀌면 다시 푼다.

### 4-2. 줄 길이

- 주석 줄 80자. 넘으면 1-4 의 들여쓰기대로 줄바꿈한다.
- 코드 뒤에 붙는 후행 주석도 합쳐서 80자 안에 넣는다. 안 되면 2-3 처럼 줄을 나누거나, 주석을 선언 위로 올린다.

## 5. 근거 인용

- 종류는 다섯이다. **`근거: 종류 — 내용`** 형식으로 쓴다.

| 종류 | 뜻 |
|---|---|
| `표준` | 공개된 표준 · API 계약 · 공식 (`표준 — 표준 중력 9.80665, 1000 / 9.80665`) |
| `인용` | 참조 자료에서 가져온 값 (`인용 — 참조 파일 값의 소수점 자리가 최대 3자리`) |
| `측정` | 우리가 직접 재본 값 (`측정 — 동일 단말 요청 주기별 검증에서 128Hz 요청 시 210Hz`) |
| `미정` | 아직 정해지지 않아 임시로 둔 것 (`미정 — 서버 로그인 API 연동 방식이 정해지면 원복 및 재작성 필요`) |
| `미확인` | 그렇게 정한 이유는 전해 들었으나 찾아갈 근거가 코드·문서에 없는 것 (`미확인 — 기준치의 표준·문서 출처를 코드에서 확인할 수 없다`) |

- 찾아갈 수 있을 만큼 구체적으로 적는다.
- 근거 자체는 있는데 그중 일부만 확인이 안 되면, `근거:` 줄 아래에 `미확인:` 을 한 단으로 이어 붙여 무엇이 미확인인지 밝힌다 (`capture_config.dart`).
- 실측값을 본문에 끼워 넣을 때는 `실측:` 으로 표시한다 (`실측: 검증 기기 2374.785us(421.2Hz), 대상 기기 2124.5us(470.7Hz)`).
- **결정 코드만 던지지 않는다** (`(RD-6)` 등). 코드는 우리만 안다 — 그 결정이 실제로 뭘 정했는지 내용을 풀어 쓰고, 코드는 있어도 그만인 부가 정보로만 둔다.
- 원본 문서가 저장소에 없으면(삭제됨 등) 코드 인용 자체를 하지 않는다. 확인 못 한 내용은 추측하지 말고 `미확인` 으로 명시한다.
- 옛 코드/문서 체계 표기(`S1`, `A-01` 등)는 새 주석에 끌어오지 않는다.

## 6. 미구현 표기

예외를 던지거나, 값을 흉내만 내거나, 빈 본문인 선언에는 `미구현:` 줄을 붙인다.

```dart
/// 작성: 2026-08-18 23:29:46 · 박건준
/// 함수: save
/// 목적: 측정 한 건을 기기에 저장한다.
/// 인자: result — 저장할 측정 결과
/// 반환: 저장된 항목의 식별자
/// 미구현: 저장 계층이 없어 UnimplementedError 를 던진다. 히스토리
///       화면(history_screen.dart)의 예시 데이터 저장 버튼이 이를
///       잡아 "측정 기록 저장" 요청이 실패했다는 스낵바를 띄운다.
Future<String> save(MeasurementResult result) => throw UnimplementedError();
```

- **무엇이 없는지 + 대신 무슨 일이 일어나는지** 둘 다 적는다. "아직 구현 안 됨" 한 줄로 끝내지 않는다.
- "대신 무슨 일이" 는 **부르는 쪽까지 따라가서** 적는다. 어느 파일 어느 함수가 그 예외를 잡아 화면에 무엇을 띄우는지까지 쓴다.
- 클래스 · 인터페이스 안의 여러 멤버가 미구현이면, **클래스 주석에도 `미구현:` 을 두고 어디까지 되고 어디부터 안 되는지 요약한다** (`measurement_repository.dart`, `prefs_store.dart`).

```dart
/// 미구현: `loadEmail()`과 `saveEmail()`만 실제로 저장·조회한다.
///       나머지(최근 현장 정보를 다루는 `loadLastSite()`,
///       `saveLastSite()`)는 예외를 던지지 않고 null 또는 빈 값을
///       돌려준다.
```

- 조용히 성공한 척하는 경우(항상 `true` 반환, 빈 Map 반환, 빈 본문)가 가장 위험하다. 반드시 적는다.
- 부르는 곳이 하나도 없는 미구현 선언은 표기 대상이 아니라 **삭제 대상**이다.

## 7. 금지

| 금지 | 이유 |
|---|---|
| 코드를 그대로 옮긴 주석 | 정보량 0, 코드 바뀌면 거짓이 된다 |
| 주석 처리한 죽은 코드 | 발견 즉시 삭제. 이력은 git 이 갖는다 |
| 부르는 곳이 없는 선언 | 삭제한다. 주석으로 설명해 남기지 않는다 |
| 날짜 · 담당 없는 TODO | `// TODO(홍길동, 2026-09-01):` 형식만 허용 |
| 추측 서술 (`아마도`, `~인 듯`) | 5장 참고 — `미확인` 으로 명시한다 |
| 비유 · 관용 표현 (`들쭉날쭉하다` 등) | 정확한 말로 쓴다 — `들쭉날쭉한 간격` 대신 `일정하지 않은 간격` |
| 영어 서술문 | 읽는 사람이 한국어 리뷰어다 |
| 함수 아래 주석 | 설명은 항상 선언 위에 |
| 파일 머리 작성 이력 | 0장 참고. 선언마다 갖는다 |
| `목적:` 만 있고 첫 라벨이 없는 블록 | 1-2 참고 |
| 인스턴스 필드에 `변수:` 라벨 | 2-2 참고. 산문으로 쓴다 |
| 테스트 · 디버그 전용 우회로 | 제품 흐름에 섞지 않는다. 주입이 필요하면 생성자 인자로만 |

## 8. 링크

- 시작 줄 = **주석 첫 줄**(= `작성:` 줄), 끝 줄 = 선언 닫는 괄호
  `.../blob/<커밋>/<경로>#L<주석시작>-L<선언끝>`
- 호출 지점을 가리키는 화살표 링크는 예외 — 호출한 줄 그대로 (`#L124`, `#L282-L291`).
- 주석 작업 완료 후 전면 재링크, 커밋 해시 최신화.
- 줄번호는 자주 밀린다. 인용한 줄번호는 **전부 실제 코드와 대조한 뒤** 결과를 보고한다.

## 9. 점검표

1. 파일 머리에 작성 이력이 남아 있지 않은가
2. 모든 선언 주석이 `작성 → 수정 → 라벨 → 목적 → 인자 → 반환 → 식 → 근거 → 미구현` 순서인가
3. 함수 · 클래스 · 생성자 · 클래스 상수에 `작성:` 이 빠진 곳은 없는가 — 단, 2-1 의 예외에 해당하는 묶음 상수는 묶음 블록에만 있으면 되고, 항목마다 라벨 블록이 없는 것을 위반으로 세지 않는다
4. `목적:` 만 있고 첫 라벨이 없는 블록은 없는가
5. 이어지는 줄이 7칸(`식:` 은 5칸, 불릿 이어짐은 9칸, 번호 목록 이어짐은 10칸)으로 맞춰져 있는가
6. 인스턴스 필드에 `변수:` 라벨을 붙이진 않았는가
7. 수식 있는 함수에 `식:` 이 있는가
8. 모든 필드 · 지역변수에 단위 · 범위 · 설명이 있는가. 시간 단위를 우리말로 적었는가
9. 미구현 선언에 `미구현:` 이 있고, 부르는 쪽까지 따라가 적었는가. 클래스 단위 요약이 있는가
10. 부르는 곳이 없는 선언 · 주석 처리된 죽은 코드가 없는가
11. 본문 주석이 "왜"만 말하는가, 코드 반복이 없는가
12. 80자 넘는 줄이 없는가 (후행 주석 포함)
13. 코드 이름을 백틱으로 감쌌는가
14. 프레임워크 용어를 쉬운 말로 풀 수 있는데 그냥 쓰진 않았는가. 첫 등장에 풀이가 있는가
15. 근거가 `표준 / 인용 / 측정 / 미정 / 미확인` 중 하나로 시작하는가
16. 결정 코드만 던지고 내용을 안 풀어 쓴 곳은 없는가
17. `로직 이동` 이 대상만 짧게, 호출부마다 하나씩 달려 있는가. 함수에 `()` 를 붙였는가
18. `로직 이동` 대상이 실제로 도달 가능한가
19. 링크 시작 줄이 주석 첫 줄인가
