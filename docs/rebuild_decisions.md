# 리빌딩 결정 기록

각 결정은 번호·날짜·내용·근거를 남긴다. 리빌딩 완료 후 학습 자료의 골격이 된다.

## RD-1 (8/6) 원본 이벤트 스트림을 1차 산출물로 삼는다
기존 구조는 256Hz 보간 스트림이 주 산출물이고 원본은 cache 덤프(부산물)였다.
새 구조는 보간 전 원본이 기준이고 보간은 후처리다.
근거: 앱이 만든 격자 시각으로 앱의 주기를 검증하면 순환 논증이 된다 (기존수집계층 판독서 §1-3).

## RD-2 (8/6) 원본 기록 형식으로 develop raw_native 형식을 채택한다
형식: `type tsUs x_mg y_mg z_mg dtUs`, `#` 줄은 주석.
근거: 간격 판정에 필요한 정보(원본 시각 + 직전 간격)가 정확히 이 구성이며,
develop 브랜치(08ef27a)가 이미 같은 형식으로 실측 파일을 생성 중이라 상호 호환된다.
기존 EVIMP1(가로 20열)은 보간 후 데이터용으로 병존하며 이 형식이 대체하지 않는다.

## RD-3 (8/6) develop 커밋 2건은 cherry-pick 하지 않고 참조로만 쓴다
대상: 96eda7f(명시 주기 요청), 08ef27a(raw_native 덤프).
근거: rebuild 브랜치의 골격화된 sensor_channel.dart 와 충돌하며,
P6·P7 에서 판독서 변경 판정(C1~C7)을 반영해 계승 구현한다.

## RD-4 (8/6) 판독 실패 줄은 0값 대체가 아니라 폐기 + 집계한다
근거: 기존 Dart 수신부는 역직렬화 실패 시 0값 샘플을 만들었고, 이는 Type B 오염
(유령 0 샘플)의 코드 내 재현 경로였다 (판독서 C5).

## RD-5 (8/6) dtUs 는 기록 당시 값을 보존하고, 검증 시 tsUs 차이로 재계산해 대조한다
근거: 같은 정보를 두 경로(네이티브 기록, 사후 재계산)로 갖게 되어
기록 무결성을 파일 자체로 검증할 수 있다.

## RD-6 (8/6) 수집 대상은 raw(accel) + gravity 2종으로 한정한다
motion 은 raw − gravity 로만 산출한다. linear(TYPE_LINEAR_ACCELERATION)는
검증되지 않았으므로 수집·산출·저장 어디에도 쓰지 않는다.
채택 여부는 raw−gravity 대비 검증 후 별도 결정한다.
NativeEventType.linear 는 develop 생성 파일과의 판독 호환을 위해서만 유지한다.
근거: 검증된 파이프라인은 Raw − Gravity = Motion (골든 픽스처로 확인).
linear 는 기존 코드의 관행이었을 뿐 검증 이력이 없다.
