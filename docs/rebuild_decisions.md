# 리빌딩 결정 기록

각 결정은 번호·날짜·내용·근거를 남긴다. 리빌딩 완료 후 학습 자료의 골격이 된다.

## RD-1 (8/6) 원본 이벤트 스트림을 1차 산출물로 삼는다
기존 구조는 256Hz 보간 스트림이 주 산출물이고 원본은 cache 덤프(부산물)였다.
새 구조는 보간 전 원본이 기준이고 보간은 후처리다.
근거: 앱이 만든 격자 시각으로 앱의 주기를 검증하면 순환 논증이 된다 (기존수집계층 판독서 §1-3).

## RD-2 (8/6) 원본 기록 형식으로 develop raw_native 형식을 채택한다
형식: `type tsUs x_mg y_mg z_mg dtUs`, `#` 줄은 주석.
근거: 간격 판정에 필요한 정보(원본 시각 + 직전 간격)가 정확히 이 구성이며,
develop 브랜치(08ef27a)가 이미 같은 형식으로 실측 파일을 생성 중이라 상호 호환된다.
기존 EVIMP1(가로 20열)은 보간 후 데이터용으로 병존하며 이 형식이 대체하지 않는다.

## RD-3 (8/6) develop 커밋 2건은 cherry-pick 하지 않고 참조로만 쓴다
대상: 96eda7f(명시 주기 요청), 08ef27a(raw_native 덤프).
근거: rebuild 브랜치의 골격화된 sensor_channel.dart 와 충돌하며,
P6·P7 에서 판독서 변경 판정(C1~C7)을 반영해 계승 구현한다.

## RD-4 (8/6) 판독 실패 줄은 0값 대체가 아니라 폐기 + 집계한다
근거: 기존 Dart 수신부는 역직렬화 실패 시 0값 샘플을 만들었고, 이는 Type B 오염
(유령 0 샘플)의 코드 내 재현 경로였다 (판독서 C5).

## RD-5 (8/6) dtUs 는 기록 당시 값을 보존하고, 검증 시 tsUs 차이로 재계산해 대조한다
근거: 같은 정보를 두 경로(네이티브 기록, 사후 재계산)로 갖게 되어
기록 무결성을 파일 자체로 검증할 수 있다.

## RD-6 (8/6) 수집 대상은 raw(accel) + gravity 2종으로 한정한다
motion 은 raw − gravity 로만 산출한다. linear(TYPE_LINEAR_ACCELERATION)는
검증되지 않았으므로 수집·산출·저장 어디에도 쓰지 않는다.
채택 여부는 raw−gravity 대비 검증 후 별도 결정한다.
NativeEventType.linear 는 develop 생성 파일과의 판독 호환을 위해서만 유지한다.
근거: 검증된 파이프라인은 Raw − Gravity = Motion (골든 픽스처로 확인).
linear 는 기존 코드의 관행이었을 뿐 검증 이력이 없다.

## RD-7 (8/6) 간격은 같은 이벤트 종류끼리만 계산한다
raw(accel)와 gravity 는 한 스트림에 섞여 도착하므로, 종류 구분 없이 간격을 재면
실제 주기의 절반 수준 값이 나와 판정을 왜곡한다.
근거: raw_native 파일 구조 (종류가 인터리브로 기록됨).

## RD-8 (8/6) 실측 주기는 평균이 아니라 중앙값으로 추정한다
운영체제의 간헐적 지연이 만드는 소수의 큰 간격이 평균을 밀어
주기를 실제보다 낮게 추정하게 만든다. 중앙값은 이에 강건하다.
근거: 측정 — 기존 로그에서 콜백 지연 스파이크 확인됨.

## RD-9 (8/6) 수집 시작 실패는 화면으로 예외를 던지지 않는다
실패 원인은 lastCaptureError 에 보존하고, 사용자 안내는 측정 화면의
3초 미수신 타임아웃이 담당한다.
근거: 화면(measuring_screen)은 수정 금지 계약 상태이며 startCapture 를
try 없이 await 하므로, 예외를 던지면 화면이 깨진다. 기존의 조용한 삼킴과 달리
원인을 보존하므로 추적은 가능하다.

## RD-10 (8/6) motion 합성은 최근 gravity 값 유지(영점 유지) 방식으로 한다
raw 이벤트마다 가장 최근에 도착한 gravity 를 붙여 raw − gravity 를 계산한다.
gravity 확보 전 raw 는 폐기·집계한다.
근거: gravity 는 저주파 성분이라 수 밀리초 유지로 인한 오차가 측정 대역에서
무시 가능하며, 보간과 달리 원본 값이 그대로 보존된다. 필요 시 시각 보간으로의
전환 여부는 실측 대조 후 판단한다.

## RD-11 (8/6) 화면·엔진에 주는 샘플의 tsUs 는 실제 센서 시각이다
기존 구조의 보간 격자 시각을 폐기한다 (판독서 D1). 샘플 간격은 불균일하며,
등간격이 필요한 후처리는 이 시각을 근거로 별도 수행한다.

## RD-12 (8/6) 우회·재작성으로 무효화된 기존 테스트는 사유를 적어 보류한다
삭제하지 않고 @Skip 으로 보류하며, 주석에 무효 사유와 복원 조건을 남긴다.
근거: 전체 테스트가 항상 실패 상태면 이후 실제 회귀가 묻힌다.
보류 목록:
- test/domain/auth_test.dart (원인 A - 로그인 우회)
- test/features/auth/login_screen_test.dart (원인 A - 로그인 우회)
- test/features/settings/settings_and_email_test.dart (원인 A - 로그인 우회)
- test/widget_test.dart (원인 C - sensor_channel 재구현)

## RD-13 (8/6) startCapture 기본값 256·85.0 은 계약 고정값으로 당분간 유지한다
UI 계약(ui_contract.md §2.5)이 시그니처 기본값을 고정하고 있어 지금은 옮길 수 없다.
계약 해제(UI 분해) 시 CaptureConfig 참조로 이관한다.
근거: 주석 규칙 "숫자는 설정 파일에만"과의 충돌을 인지한 상태의 의도적 예외.
