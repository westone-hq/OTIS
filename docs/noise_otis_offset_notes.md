# 소음(dBA) 오프셋·OTIS 차이 정리

작성: 2026-09-28 · 박희정  
관련 브랜치: `test/dB`  
관련 커밋 예: `fix(noise): OTIS 맞춤으로 dBA 오프셋 87.3 및 초반 0 보간`

---

## 한 줄 요약

**+85는 “임시 기본값”이지 최종 규격이 아니다.**  
결국엔 OTIS/소음계에 맞춰 바꾸는 게 정상이다.

---

## +85를 평생 고정할 필요는 없다

처음부터 임시값이었다.  
(dBFS를 사람이 보는 dB 근처로 옮기려고 넣은 것)

### 앞으로 어떻게

| 단계 | 하는 일 |
|------|---------|
| **지금** | +85로 대략 레벨 보기 |
| **OTIS랑 맞출 때** | 동시 측정으로 오프셋만 조정 (예: 87~88) |
| **제대로 할 때** | 소음계로 교정해서 기기/현장별 오프셋 저장 |

식은 대략 이렇게 본다.

```text
dBA ≈ dBFS + micDbfsToDbaOffset + calibrationOffsetDba
```

- `micDbfsToDbaOffset` — 기본 옮김값 (예: 예전 85.0 → OTIS 맞춤 87.3)
- `calibrationOffsetDba` — 현장·기기별 추가 보정 (나중에 소음계 교정으로 저장)

코드 쪽 기본값 위치:

- Dart 상수: `lib/domain/capture/noise_offset.dart` (`kDefaultMicDbfsToDbaOffset`)
- Android: `NoiseCaptureHandler` / `MainActivity` 기본 인자
- 측정 시작: `sensor_channel.dart` / `measuring_screen.dart`

## 왜 OTIS랑 차이가 나는지

### 1. 오프셋(+85)이 임시값

- 우리는 `dBFS + 85`(또는 조정된 오프셋)로만 맞춤.
- OTIS는 자기네 교정값.
- → 절대 dB가 Exact 같을 이유가 없음.
- 동시측정 비교에서는 우리가 약 **2~3 dB 낮음** → 오프셋을 예: **+87~+88** 쪽으로 올리는 게 1순위.

### 2. 창 길이(지금 0.03125초 실험값)

- 처음에는 Slow 1.0초, 그다음 OTIS 출렁임에 맞추려고 Fast 0.125초로 바꿨다.
- 지금(2026-10-05)은 피크가 눌리는 문제를 보려고 **0.03125초** 창을
  1초에 **512번** 밀며 갱신하는 실험값을 쓴다
  (`NoiseCaptureHandler.kt` 의 `WINDOW_SEC` · `HOP_HZ`).
- OTIS도 빠르게 바뀌는 형태일 수 있음.
- → Slow보다 피크·변화에 더 민감하다.

### 3. A가중 없음

- 사람 귀 특성 필터가 없음. OTIS는 있을 수 있음.
- → 주파수 반응 차이로 숫자 어긋남.

### 4. 초반 0

- Slow/Fast 창이 채워지기 전 값이 **0**으로 들어감.
- OTIS는 처음부터 값이 있음.
- (네이티브 쪽: 창이 가득 차기 전에는 RMS를 값으로 내보내지 않음 — `NoiseCaptureHandler`)

### 5. 파일에 쓰는 방식

- OTIS는 거의 매 줄 소음이 미세 변화.
- 우리는 같은 값이 몇 줄 반복되는 편.
  - 이유: 창을 격자(~256 Hz) hop으로 밀어도, 1초 창이라 값이 천천히 바뀜.
  - 격자에서는 앞뒤 실측 사이 **선형 보간**을 함 (`grid_resampler`).

## 어떻게 고치는 게 좋은지 (순서)

### 1순위 — 오프셋 조정

동시 측정 기준으로 `+85` → OTIS 평균에 맞게 (예: `+87`~`+88`).

- 제일 빠르고, 절대값 차이부터 줄어듦.
- **+85는 임시 기본값이라 계속 고집할 필요 없음.**
- 현재 `test/dB`에서는 기본을 **87.3**으로 올려 둔 상태 (약 −2.3 dB 보정).

### 2순위 — 초반 0 처리

창이 1초 채워진 뒤부터만 파일에 쓰기 (또는 그전은 홀드/미기록).

현재 적용된 방식은 아래 **「초반 noise 0 채우기」** 참고.

### 3순위 — 갱신 모양 맞추기

필요하면 Slow(1.0초)로 되돌리거나, 격자에서 소음 보간을 더 촘촘하게.

### 4순위 — A가중 (나중)

교정 장비 없으면 효과 검증이 어려움.  
오프셋 맞춘 뒤에 한다.

## 「초반 noise 0 채우기」가 무슨 소리인지

### 문제

소음은 **최근 창 길이(지금 0.03125초)** 분량의 마이크 샘플로 RMS를 낸다.

측정 시작 직후 창 길이만큼은 창이 아직 안 찼다.

그래서 네이티브는 그동안 `latestDba = 0` 을 보낸다  
→ 격자/EVIMP1 파일 앞부분에 **소음 열만 0이 길게** 찍힌다.

OTIS 파일은 처음부터 소음 숫자가 있다.  
그래서 동시측정 파일을 나란히 보면 “우리만 초반이 0”으로 보인다.

### 코드가 한 일 (`grid_resampler`)

격자(256 Hz 표)를 다 만든 뒤:

1. 맨 앞에서부터 `noiseDba == 0` 인 구간을 찾는다.
2. **처음으로 0보다 큰 값**이 나온 행의 소음값을 기억한다.
3. 그 앞의 0들만, 그 첫 유효값으로 **같은 숫자로 채운다**(홀드/백필).

예:

```text
전:  0, 0, 0, 0, 48.2, 48.3, 48.1, ...
후: 48.2, 48.2, 48.2, 48.2, 48.2, 48.3, 48.1, ...
```

진동 X/Y/Z는 건드리지 않고, **소음 열만** 건드린다.

함수: `GridResampler._backfillLeadingNoiseDba`

### 이게 “진짜로 그 순간을 재측정”한 건 아님

- 창이 비어 있던 구간의 **실측을 복원한 게 아니라**,  
  “파일/리포트에 초반 0이 길게 안 보이게” **첫 유효값으로 메운 것**이다.
- 문서의 2순위 대안인 “창 찬 뒤부터만 기록 / 미기록”과는 다른 선택이다.
  - 지금 선택: **홀드(첫 유효값으로 채움)** → OTIS처럼 처음부터 숫자 있게 맞춤.
  - 다른 선택: 앞 1초를 파일에서 빼거나 0(미측정)으로 남겨 두고 리포트에서 0은 평균에서 제외.

### 네이티브와의 역할 분담

| 구간 | 역할 |
|------|------|
| `NoiseCaptureHandler` | 창이 덜 찼으면 **값을 안 내고 0** (가짜 경사 RMS 방지) |
| `grid_resampler` 백필 | 격자 완성 후, 앞쪽 0만 **첫 유효값으로 채움** (파일 초반 0 줄이기) |

즉 “덜 찬 창의 RMS를 값처럼 쓰지 않는다”는 규칙은 유지하고,  
파일에만 초반이 비지 않게 메운 것이다.
