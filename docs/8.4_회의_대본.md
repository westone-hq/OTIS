# 8.4 회의 대본 — 1~3ms / 3~7ms 요청 주기 비교

발표 자료: `docs/8.4 회의.html`  
대상: 교수님 · 요청 주기 실측 + Android 공식 API 근거

---

## 1. 오프닝 (표지)

안녕하세요. 오늘은 센서 이벤트 요청 주기를 **1~3ms**와 **3~7ms**로 나눠 동시에 받아 본 결과를 보고드리겠습니다.

핵심만 먼저 말씀드리면, 코드에서 요청 방법은 다르게 걸었지만 **이 단말기에서는 실측 결과가 사실상 같았습니다.** 이유는 Android API의 주기 값이 “보장”이 아니라 “요청”이기 때문입니다.

이어서 실측 파일 → 코드 → 공식 문서 근거 → 최종결론 순서로 설명하겠습니다.

---

## 2. 실측 파일 (슬라이드 02)

같은 엘리베이터 운행을 측정하면서, 센서 구독을 **두 갈래로 동시에** 걸었습니다.

- 왼쪽 `raw_3to7ms_초별.txt` → `SENSOR_DELAY_FASTEST` 요청  
- 오른쪽 `raw_1to3ms_초별.txt` → `samplingPeriodUs=3000` (3ms) 요청  

둘 다 보간하지 않고, 256개로 자르지도 않은 **원본 이벤트**를 초 단위로 모은 파일입니다.

약 29초 구간에서 총 이벤트는 왼쪽 24,416개, 오른쪽 24,436개로 거의 같습니다. 특히 1초 구간을 보면 raw가 약 421개, gravity·linear가 각각 약 210개대, 합계 약 843개로 양쪽이 맞춰집니다.

raw 기준 간격으로 환산하면 대략 **2.375ms**, 초당 약 421Hz입니다.

**포인트:** 요청 문구만 “3~7ms / 1~3ms”로 다를 뿐, 이 폰이 실제로 준 속도는 같았습니다.

---

## 3. 코드 1 — FASTEST와 3000 동시 등록 (슬라이드 03)

실제 코드는 Android 공식 `SensorManager.registerListener`입니다. 세 번째 인자가 주기입니다.

**A쪽**은 `SENSOR_DELAY_FASTEST`입니다. 공식 Sensors Overview에 FASTEST는 **0 microsecond delay**, 즉 “가능한 한 빨리”라고 되어 있습니다. 저희가 예전에 쓰던 방식이고, 현장에서는 대략 3~7ms 간격으로 오는 경우가 많아서 그렇게 표현해 왔습니다.

**B쪽**은 같은 함수에 숫자 **3000**을 넣었습니다. Android는 주기를 마이크로초로 받으므로 3000µs = 3ms입니다. Overview에도 API 11부터 µs 정수를 직접 넣을 수 있다고 명시되어 있습니다. 임의 해킹이 아니라 공식 overload입니다.

리스너를 둘로 나눈 이유는, 한쪽은 분석(256Hz 리샘플)과 원본 덤프를 같이 하고, 다른 쪽은 원본만 받아 파일로 비교하기 위해서입니다. 센서는 동일하게 걸어 공정하게 비교했습니다.

**예상 질문 — “왜 3000이냐?”**  
→ “3ms를 코드에 분명히 쓰기 위한 **요청값**입니다. 보장은 아닙니다.”

**레퍼런스**
- https://developer.android.com/reference/android/hardware/SensorManager  
- https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview

## 4. 코드 2 — 요청 ≠ 실측 (슬라이드 04)

여기가 가장 중요합니다. 공식 SensorManager 문서는 `samplingPeriodUs`를 **desired delay**, 즉 “원하는 지연”이라고 씁니다. 하드웨어 보장 주기가 아닙니다.

그래서 “1~3ms로 측정했다”고 말하면 오해가 생깁니다. 정확한 말은  
**“3ms로 요청했고, 실제 간격은 timestamp로 확인했다”**입니다.

실측 방법은 단순합니다. `SensorEvent.timestamp`는 나노초 단위 공식 필드입니다. 연속 이벤트의 시각 차이를 마이크로초·밀리초로 바꾼 값이 초별 파일의 `dt_ms`입니다.

그 결과, 요청은 3000µs였는데 실제는 약 **2.375ms**였고, FASTEST 쪽도 같은 값이었습니다. 즉 이 기기의 센서/드라이버 상한에 양쪽이 같이 걸린 것입니다. 1ms처럼 더 촘촘히 받는 것은 요청만으로 되지 않았습니다.

**예상 질문 — “그럼 코드가 잘못된 거 아니냐?”**  
→ “아닙니다. 공식 API의 요청/실측 분리 동작을 확인한 결과입니다.”

**레퍼런스**
- https://developer.android.com/reference/android/hardware/SensorManager  
- https://developer.android.com/reference/android/hardware/SensorEvent

## 5. 코드 3 — onSensorChanged (슬라이드 05)

센서 값은 저희가 폴링하는 게 아니라, Android가 `onSensorChanged`를 호출해 줍니다. `SensorEventListener` 공식 콜백입니다.

`event.timestamp`는 발생 시각(나노초), `values[0/1/2]`는 X/Y/Z입니다. 가속도 계열 단위는 m/s²이고, 파일/보고서용으로는 mg로 환산해 저장합니다. 축 순서 0·1·2는 Android 규격이라 바꾸지 않습니다.

파일의 type 이름 `raw`는 예전 `rawX/Y/Z`와 같은 `TYPE_ACCELEROMETER`입니다. gravity는 중력 성분, linear는 중력 제외 가속도이고, 진동·거리·속도 분석의 주축은 linear 쪽입니다.

참고로 거리·속도·진동 계산 입력은 이 불규칙 원본을 그대로 쓰지 않고, 256Hz로 맞춰 보간한 `raw.txt`를 사용합니다. 오늘 보여 드린 초별 txt는 **요청 주기와 실측 주기를 검증**하기 위한 근거 자료입니다.

**레퍼런스**
- https://developer.android.com/reference/android/hardware/SensorEventListener  
- https://developer.android.com/reference/android/hardware/SensorEvent

## 6. 최종결론 (슬라이드 06)

정리하면, **최종결론은 차이 없음**입니다.

이 단말기에서 FASTEST와 3000µs 요청은 둘 다 약 2.375ms, 초당 raw 약 421개로 같았습니다.

이유는 두 가지입니다.

1. 3000은 보장이 아니라 **요청값**입니다.  
2. 이 폰의 공급 상한이 이미 그 근처라, 더 공격적인 FASTEST와 3ms 요청이 같은 속도에 수렴했습니다.

코드는 Android 공식 SensorManager / SensorEventListener / SensorEvent를 따랐고, 레퍼런스 링크는 슬라이드 하단에 적어 두었습니다.

이상입니다. 질문 있으시면 받겠습니다.

## Q&A 대비

**Q. 1~3ms로 측정한 거냐?**  
A. 아닙니다. 3ms로 **요청**했고, 실측은 timestamp로 약 2.375ms였습니다.

**Q. 코드가 잘못된 거 아니냐?**  
A. 아닙니다. 공식 API의 desired delay 동작을 확인한 결과입니다.

**Q. 더 촘촘히(1ms) 받을 수 있나?**  
A. 이 기기에서는 요청만으로 안 됐습니다. 센서/드라이버 상한입니다.

**Q. 분석은 뭘 쓰나?**  
A. 초별 txt는 검증용이고, 거리·속도·진동은 256Hz 리샘플(`raw.txt`)을 사용합니다.

**Q. FASTEST랑 3000이 왜 같냐?**  
A. FASTEST는 “가능한 한 빨리(0µs 요청)”, 3000은 “3ms를 원함”인데, 이 폰 상한이 ≈2.4ms라 둘 다 그 속도에 걸린 것입니다.
